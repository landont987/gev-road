# Smoothness pass 2026-10-20

Goal: make the map run smoothly on the head unit (Android 9, 2 GB, MediaTek MT8163, WebView 66) before the first truck test. Measured on the computer, so every number here is a stand-in for the truck; the truck numbers come from the menu's MEMORY line and the first drive.

## How it was measured
- Browser preview (`node scripts/dev.mjs`) at 1280x720 with the demo drive in drive mode.
- Chrome performance traces at a 6x CPU slowdown, read with a small script that sums main-thread time by event. A first trace was thrown out: a real mouse over the window added 625 hit tests and 29 wheel zooms.
- Heap and DOM counts read from the page every 30 s during a 2.5 minute drive.
- The AZ511 event feed fetched from node with the app's User-Agent to time the parse.

## What the profile said

The page's own work is small. On a weak GPU the cost is compositing: each DOM marker is its own layer, and every GPS recenter moves the pane. That is why the marker count was the first fix.

## Changes (0.3.11 and 0.3.12)
- **#47 Draw only on-screen dots.** A shared dot layer keeps markers for the screen plus half a screen of margin, re-checked on `moveend`. Spoken alerts and the truck check read the full lists.
- **#48 Memory line in the menu.** The unit's free memory, Android's low-memory flag, and the app process. On Android 9 the map page runs in a WebView process the app cannot list, so the line says so.
- **#51 Tiles kept on the unit for 30 days.** The app answers OpenStreetMap tile requests from disk, fetches and saves what is missing, and serves a stale copy when the hotspot drops. 150 MB cap, oldest first.

## Sweep two (0.3.13)
Two reviewer passes over the page modules and the Android shell found no Chrome 66 API gaps, no unbounded growth and no hotspot hammering. Fixed: re-follow after a drag while moving (#53), no "Drive here?" while moving (#54), the data meter read every 5 s not every fix (#55), stream restart on ended/stalled (#56), three small guards (#57), USB claim retries (#58), big HTTP answers pulled by the page instead of pushed as a script literal (#59), the radio drawer's WebView built on open and freed on STOP (#60), voice: validated online state and engine rebuild (#61).

## Left alone, and why
- **The event feed's 2.4 MB every 5 minutes** no longer crosses as a script literal (#59, 0.3.13). JSON.parse of it on the unit is still a short hitch, measured at 3.5 ms on the computer.
- **Startup forced layout (213 ms at 6x)** is Leaflet's first size read on the first `setView`, which is the page's first layout. Unavoidable and one-time.
- **Lazy radio drawer WebView.** All WebViews in one app share one renderer process on Android 9, so creating it at startup costs little.
- **A long parked drag past half a screen** may show an empty edge until the finger lifts. Drive mode disables dragging.
